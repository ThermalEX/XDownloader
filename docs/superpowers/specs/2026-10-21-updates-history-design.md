# GitHub 发布、应用更新与下载历史设计

日期：2026-10-21（Europe/London）

状态：用户已于 2026-10-21 通过设计；实施计划待审阅，尚未实施。

工作目录：`<workspace>`；保留 `feature/flutter-material3` 分支。

## 目标与约束

用户希望公开上传 GitHub，之后直接在手机检查和安装更新，免去反复连接电脑；可以选择稳定版或 Beta 版。同时提供独立下载历史，删除文件后仍能找回原链接。继续采用 Flutter Material 3、Android 首发，保留现有分享、播放、下载、收藏和隐私功能。

使用原签名、原包名和递增的 Android versionCode。保留本地完整 Git 历史、所有历史 APK 和校验值；不在仓库根目录放 APK，不清空生产数据。首次安装带更新功能的版本仍需安装一次 APK，之后在应用内完成后续更新流程。

## 方案选择

采用公开的 `ThermalEX/XDownloader` 源码仓库和 GitHub Releases：应用检查发布信息、下载并验证安装包，再调用 Android 系统安装器。保留浏览器下载作为网络或安装流程异常时的备用入口。

只跳转浏览器虽更简单，但缺少应用内进度、版本选择和校验体验；私有仓库配公开分发服务会增加维护成本。当前不引入这两种方案，也不依赖 root 静默安装。

## 公开仓库与发布边界

旧 Git 历史含用户上传的私人截图，不能直接推送原分支或全部标签。以审查过的源码快照建立独立公开 `main` 基线，保留本地原仓库、分支和标签，避免重写已有历史。

公开内容包含源码、测试、安全的合成样例、构建说明、贡献指南和本轮设计。排除 `.codex-remote-attachments/`、设备截图、设备日志、个人配置、签名材料、临时计划执行记录，以及包含私人内容的旧验收附件；公开文档相应修复引用。测试样例、文档和构建脚本也要检查凭据、私人内容和本机专用路径，签名只保留配置示例。

历史 APK 原样留在本地 `releases/`，不批量公开；本次验证的新 APK、校验清单和更新清单作为 Release assets 发布。后续使用明确的发布导出流程更新公开分支，只推送经审查的提交，不将私有分支合并到公开分支，不使用 `push --all`、`--mirror` 或批量推送旧标签。记录本地源提交与公开发布提交的对应关系，便于复现。

## 更新页面和渠道

设置的“其他”组增加“应用更新”二级页面，显示当前版本、所选渠道、检查结果、更新说明、包大小及操作状态。“关于”增加公开仓库入口，当前版本从安装包读取。

- 默认稳定版，仅接收非草稿、非 prerelease 的正式发布。
- Beta 渠道接收正式发布及 GitHub prerelease，按有效发布清单中的 versionCode 选择最新兼容版本，不能只依赖发布日期或字符串排序。
- 渠道切换持久化并重新检查；旧检查结果失效。下载中的渠道切换先要求取消当前更新下载，避免显示与安装不同渠道的包。
- 只推荐 versionCode 大于当前安装版本的包。Beta 切回稳定版时若没有更高的稳定版本，说明当前已安装测试版、等待后续稳定版，不自动降级或卸载。
- 手动“检查更新”始终可用。启动检查开关默认开启，每 24 小时至多自动检查一次，异步执行；自动检查失败不打断解析、分享和播放。手动失败显示原因与重试，自动发现新版显示非阻塞入口。
- 显示可用更新后由用户选择下载；不自动下载安装。进度可见，支持取消与失败重试；关闭页面或应用进后台不取消原生下载。

## 发布清单与版本规则

每个正式版或 Beta Release 附加 `update.json`，包含 schema 版本、versionName、递增 versionCode、渠道、包名、最低 Android API，以及每个 APK 的文件名、ABI、字节数和 SHA-256。更新说明来自同一 Release，作为普通文本显示。

稳定标签示例 `v2.5.0`，测试标签示例 `v2.6.0-beta.1`；二者共享严格递增的 versionCode 序列。GitHub prerelease 标记必须与清单渠道一致。发布工具从构建产物读取真实版本、包名和 ABI 后生成清单，不能手工填写与 APK 不一致的数据。

应用分页查询 GitHub Releases，最多检查最近 100 个 Release；忽略草稿、不完整或无兼容资产的发布。只有取得并验证清单后才能成为候选。优先选择设备支持的独立 ABI 包，否则选择通用包；ARM64 包不能被选给不支持的设备。无有效候选或超过扫描范围时明确说明检查范围，并提供发布页入口，不谎称已是最新版。

清单、API 响应和下载地址只接受 HTTPS、预期仓库及发布资产路径；应用 HTTP 客户端处理 GitHub 官方资产重定向时仅允许明确列出的官方 HTTPS 下载主机，限制重定向次数。限制元数据大小、单包大小（200 MiB）、请求时间和并发检查次数。处理离线、限流、超时、损坏 JSON、撤回发布及缺失资产；不嵌入 GitHub 令牌，不使用第三方下载代理。

计划阶段澄清（随实施计划审阅）：DownloadManager 的内部重定向由 Android 处理，应用不能逐跳拦截。原生只提交预期仓库的 HTTPS APK 地址，安装信任由最终大小、哈希和与当前安装相同的签名保证；不声称系统内部每一跳都由应用白名单控制。若要求该额外限制，需要改用原生持久化下载 worker，不能沿用当前 DownloadManager 方案声称满足。

## 更新组件与 Android 安装流程

纯 Dart 的 Release 客户端解析 API、清单和渠道规则，可注入 HTTP 客户端。更新仓库拥有检查状态、候选版本和持久化偏好；页面只发出操作并展示状态。原生更新适配器独立于现有视频下载、校验和 MediaStore 发布管线。

原生使用 DownloadManager 下载到应用专用更新目录，持久化任务编号和候选身份，重启后恢复状态；一个时间只允许一个更新下载。取消仅删除自身任务与未安装的更新包，不影响视频。网络传输失败可以重新下载，本轮不承诺自行实现跨任务断点续传。

下载完成后先在后台验证长度和 SHA-256，再读取 APK 信息，要求包名与生产包相同、versionCode 与候选一致且高于已安装版本、签名与当前已安装应用一致、系统版本满足要求。不使用清单提供的证书作为信任根；不合格文件不得进入安装器。

使用受限的 FileProvider 更新目录和临时读取授权交给系统安装器。按需引导用户授予“允许安装未知应用”；从授权页返回后恢复操作并重新校验包。安装前再次确认候选和文件身份，防止陈旧异步结果安装其他包。用户取消安装后保留“继续安装”入口；应用重启后以实际安装版本确认升级成功并清理过期缓存。

## 下载历史的数据和入口

下载页工具栏增加“下载历史”入口，不增加第五个底部标签。历史按时间倒序，展示名称、当地时间、状态和原帖子链接，区分进行中、成功、失败、取消。支持全部／成功／失败／取消筛选、重新解析、单条删除和确认后清空；重新解析跳回现有解析流程并重新获取媒体地址，避免重用过期视频 URL。没有原帖链接的旧记录显示原因，禁用重新解析。

历史与下载列表逻辑独立：删除视频或移除下载列表条目保留历史；删除历史不删除视频、不取消活动任务。更改已有菜单和清空操作的说明，明确影响范围。用户清空历史后活动任务仍继续，不会在结束时重新创建被清除的同一历史项；之后显式重试作为新任务产生新历史。

在现有 downloads 快照内增加历史集合、迁移标记和历史删除抑制信息，复用串行队列与原子快照写入。同一任务开始、结束等状态转换与对应历史变更在一次快照中保存，进度字节变化不逐次写历史。历史只存任务 ID、显示名称、原帖链接、开始／结束时间及状态，不额外复制下载请求头、临时媒体地址或封面缓存。

首次升级从现有下载记录幂等迁移，使用原任务 ID 去重；无法恢复此前已删除的记录。迁移标记防止清空后的历史从旧记录再次出现。用户删除历史时保存必要的抑制信息，原生任务恢复或补发回调不能复活历史。记录存储失败需显示明确错误，不能假装已清空；下载文件本身继续按既有原生机制恢复。

隐私模式下历史页隐藏名称、链接、时间分组以外的内容与无障碍描述，使用通用占位；禁用复制和重新解析，提示隐私模式已启用。列表、菜单、确认框、路由返回及异步回调都检查当前隐私状态，保留删除和清空能力。

## 验证与交付

- 离线覆盖稳定／Beta 选择、乱序发布、递增版本、切回稳定不降级、分页、兼容 ABI、缺失或损坏清单、错误地址、限流、超时和渠道切换竞态。
- 原生 probe 覆盖更新下载恢复、取消隔离、哈希／包名／签名／版本拒绝、授权返回与安装器交接；测试专用接口不得进入 production。
- 历史覆盖旧快照迁移、重启、成功／失败／取消、文件删除后保留、独立清空、活动任务删除抑制、重复回调、写入失败和隐私限制。
- 验证 Material 3 深浅色、320dp、两倍字号、点击尺寸、页面返回及分享进入现有任务，保留播放器与收藏回归。
- 执行格式化、分析、离线测试及可连接的指定 Pixel probe。无可用真机时明确记录未验证项，不用模拟结果冒充安装验收。
- 构建唯一新版本（计划 `2.5.0`，实际 versionCode 在实施时检查后递增），验证原证书、全部历史 APK 校验值、生产包排除 probe 代码及公开导出内容。
- 审查公开基线后创建公开仓库，先上传完整 Release 草稿及资产并核对下载字节和清单，再发布；稳定版使用正式 Release，未来 Beta 使用 prerelease。
- 用匿名请求验证发布发现和资产下载；真实覆盖升级验证必须针对后续更高 versionCode 的测试构建或后续发布完成。首次正式版发布本身不能证明完整未来升级链路已通过，不为演示而发布假更新。
